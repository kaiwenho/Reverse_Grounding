# plan-core

The query plan contract. A JSON Schema, Pydantic models that mirror it,
semantic validators, and the pinned Biolink Model everything is checked
against.

Every other package depends on this one, and this one depends on none of them.
A plan that validates here is the only thing the planner may emit and the only
thing the executor will run.

---

## Why a plan and not TRAPI

The model writes a **plan**, never TRAPI. `plan_executor/trapi_builder.py`
derives TRAPI from a validated plan afterwards.

That split buys two things. Malformed TRAPI becomes impossible — the query
graph is generated by code from a document that has already passed a schema.
And a plan is legible: it names entities by surface string with a Biolink
category, lists paths as hops, and states its ranking rules, so a human can
read one and say "that is not the question I asked" without knowing TRAPI.

The plan is also backend-agnostic. Swapping ARAX for another Translator
endpoint means writing a new executor against this contract, not a new planner.

## What a plan contains

Required at the top level: `plan_version`, `biolink_version`, `question`,
`interpretation`, `plan_mode`, `entities`, `confidence`.

`plan_mode` picks the shape:

| mode | meaning |
|---|---|
| `discovery` | variable-endpoint paths — find candidates |
| `explanation` | two fixed endpoints — explain how they connect |
| `hybrid` | both: find candidates, then explain each one |

The rest:

- **`entities`** — named things, each with an `entity_ref`, a surface `name`,
  a `biolink_category`, and `is_variable` for the slot the answer fills.
  Names are strings; resolution to CURIEs happens in the executor, under model
  review, with the alternatives recorded.
- **`paths`** — ordered hops between entity refs. Order is ranking priority.
- **`explanation_queries`** — endpoint-to-endpoint path searches.
- **`ranking`** — `discovery` and optional `final` criteria, drawn from a
  closed list (`knowledge_level`, `num_publications`, `edge_evidence_strength`,
  `clinical_trial_phase`, …), plus how explanations may influence candidate
  order.
- **`evidence_policy`** — filters and thresholds, tagged with whether the user
  asked for them or the planner suggested them. The distinction matters
  downstream: the loop may loosen its own suggestions and may never loosen the
  user's.
- **`refusal`** — a plan may decline instead, with a typed reason.

## Validation, in two layers

```python
from plan_core import validate_plan

result = validate_plan(plan_dict)
if not result.ok:
    for err in result.errors:
        print(err)
```

**`validate_schema`** runs the JSON Schema — shape, required fields, closed
enums, no unknown properties anywhere.

**`validate_semantics`** runs what JSON Schema cannot express cleanly:
identifier uniqueness, graph connectivity, hybrid-mode wiring, answer-variable
rules, ranking shape, complete explanation fan-out, terminal refusal shape,
deprecated-predicate rejection, qualifier-family compatibility, predicate
direction against Biolink metadata, and that every declared entity is actually
queried.

`validate_plan` runs both and returns one `ValidationResult`. A plan that
fails is handed back to the planner with the errors appended, or refused.

Two checks worth knowing about, because they exist to stop a specific kind of
confident nonsense:

- **Predicate direction.** Biolink records a domain and range per predicate.
  A hop that runs one backwards is rejected here rather than returning nothing
  from the graph and looking like an absence.
- **Entities are used.** A plan may declare a concept from the question and
  then never query it. The run succeeds and returns real, well-evidenced
  answers — to a smaller question than the one asked. Nothing downstream can
  see that, so it is caught here and in the controller.

## The Biolink Model is a download

`data/biolink-model.yaml` is **not in the repository**. It is a version-pinned
dependency, gitignored, and fetched:

```bash
make biolink           # from the repo root; `make install` does this too
```

or by hand, per [`data/README.md`](data/README.md).

Nothing works without it. The schema on disk carries small illustrative enums
for readability; `compile_schema` replaces them at runtime with the real ones
read from the YAML — every Biolink category, the full aspect and direction
qualifier enums, causal mechanisms, agent types. A clone that skips this step
fails in the planner with a traceback that never mentions Biolink.

Upgrading Biolink is dropping in a new YAML and changing
`biolink_version` in plans. No code changes.

## API

```python
from plan_core import (
    QueryPlan,                  # Pydantic model of a plan
    validate_plan,              # schema + semantics, the one to call
    validate_schema,            # shape only
    validate_semantics,         # cross-field only
    ValidationResult,
    ValidationError,
    compile_schema,             # schema with Biolink enums substituted
    load_biolink_vocabulary,    # predicates, categories, qualifiers, metadata
    BiolinkVocabulary,
    archetype_tags,             # question archetypes the planner recognises
)
```

`QueryPlan` and friends are deliberately **more permissive** than the schema:
predicate, category and qualifier fields are typed `str`, not enums, because
the Biolink enums are large and change per version. The models are for
building and manipulating plans in code; the schema layer is where the
constraints live. Do not treat a plan that constructs cleanly as a plan that
validates.

## Tests

There are none yet, and that is the gap most worth closing in this package.
Two bugs so far have lived precisely in the seam between this schema and a
package reading it: a dependency pinned against the plan schema version rather
than the package version, and an executor field the schema forbade, which made
a whole feature unreachable for months without anything saying so.

Both were invisible from either side alone.
